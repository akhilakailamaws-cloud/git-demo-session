🌿 Branching Strategy

  • main — Production. Always stable. Never commit directly.
  • develop — Integration branch. All features merge here first.
  • feature/* — One branch per feature. Branch from develop.
  • ▸ hotfix/* — Emergency fix. Branch from main directly.

✍️ Writing Good Commit Messages

Conventional Commits Format

# Format:
type: short description (max 72 chars)

# Types:
feat     → new feature
fix      → bug fix
docs     → documentation only
refactor → code change, no feature/fix
chore    → build, config, tooling

# Good examples:
feat: add user login page
fix: resolve null pointer in auth service
docs: update README with deployment steps
chore: update .gitignore

🗜️ Squashing Commits

Devs make many small "wip" commits while working. Before merging, we squash them into 1 clean commit.

# You have 3 messy commits:
abc1234  wip: started team section
def5678  wip: added names
ghi9012  fix typo

# Squash last 3 into 1:
git rebase -i HEAD~3

# In editor — change to:
pick   abc1234  wip: started team section
squash def5678  wip: added names
squash ghi9012  fix typo

# Write new clean message:
feat: add team members section

# Result: 1 clean commit ✅

🏷️ Production Tags — Versioning

Tags are permanent bookmarks on a commit. Use them to mark every production release.

# Annotated tag (recommended for production)
git tag -a v1.0.0 -m "Release v1.0.0 — initial launch"
git tag -a v1.1.0 -m "Release v1.1.0 — added team section"

# Push tags to GitHub
git push origin --tags

# List all tags
git tag

# See full tag details
git show v1.1.0

# Semantic Versioning:  MAJOR.MINOR.PATCH
v1.0.0  → first stable release
v1.1.0  → new feature added
v1.1.1  → hotfix / patch

🌐 Deployment — GitHub Pages

  • Free static hosting directly from your GitHub repo
  • Go to repo → Settings → Pages
  • Source: Deploy from branch → main → / (root)
  • Save → site is live in ~60 seconds
  • URL: https://<username>.github.io/git-demo-session

Every push to main = automatic redeploy. This is your CD pipeline.


For real apps: replace GitHub Pages with AWS S3 + CloudFront, EC2, or ECS — same Git tag triggers the deploy.

🚨 Hotfix Workflow

Bug in production? Never fix on develop. Branch from main directly.

# Branch from main
git checkout main
git checkout -b hotfix/fix-version-badge

# Make fix, commit
git commit -m "fix: correct version badge text"

# Merge to main + tag
git checkout main
git merge --no-ff hotfix/fix-version-badge
git tag -a v1.1.1 -m "Hotfix v1.1.1"
git push origin main --tags

# Also merge back to develop (keep in sync!)
git checkout develop
git merge --no-ff hotfix/fix-version-badge
✅

Key Takeaways

  • Never commit directly to main
  • Use feature branches for every change
  • Squash WIP commits before merging
  • Write meaningful commit messages
  • Tag every production release with semver
  • Hotfixes branch from main, merge to both main + develop
